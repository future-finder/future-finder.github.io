NovelST：长篇文本交互式 AI 系统探索

一个仍在开发中的长篇文本交互系统探索，关注状态一致性、证据检索与验证。

进行中长文本状态管理

项目起点

NovelST 最开始来自一个很具体的问题：

如果让大语言模型长期参与一个长篇文本世界中的交互，怎样尽量避免它在不断生成的过程中逐渐忘记已有事实、混淆人物状态，或者生成与原文和历史状态相冲突的内容？

短对话中，这些问题有时并不明显。

但当背景文本扩展到上千章、人物关系和事件不断积累以后，仅仅依靠上下文窗口或者普通的检索已经很难维持长期一致性。

因此，我开始尝试把这个问题拆成几个更具体的部分：

  • 原始文本怎样整理成稳定、可检索的知识来源；
  • 哪些状态应该由程序维护，而不是交给模型自己记忆；
  • 模型生成的结果怎样经过检查后才能写回系统；
  • 当生成失败或状态冲突时，系统怎样处理。

NovelST 就是在这个过程中逐渐形成的。

它目前仍然是一个未完成的个人探索项目。我更看重这个过程中逐渐形成的系统设计思路，而不是把它描述成一个已经成熟的软件产品。

为什么单纯依赖大模型不够

最初考虑这个问题时，我很容易把重点放在模型本身：

是否可以通过更长的上下文、更强的模型或者更好的提示词解决？

但继续往下做以后，我逐渐觉得，很多问题实际上并不应该完全交给模型解决。

例如：

  • 一个角色现在是否知道某件事；
  • 某个事件是否已经发生；
  • 某个状态从什么时候开始有效；
  • 一段信息来自原著、模型推断还是此前生成结果；
  • 两条状态发生冲突时，哪一条应该被保留。

这些问题如果只依赖自然语言上下文，很难长期保持稳定。

因此，我开始把系统中的信息分成两类：

模型负责生成和推理，程序负责保存需要长期保持一致的状态。

这是 NovelST 中一个比较重要的设计出发点。

文本与证据

原始小说大约有 1070 章。

在前期处理中，我尝试把原始文本整理成更稳定的检索单位。历史记录中，确定性语料经过处理后约形成 98,630 个稳定段落。

这样做的目的不是简单地把小说“切块”，而是希望后续检索得到的文本具有相对稳定的身份。

如果同一段原文在不同阶段被反复重新切分，很多引用、状态关联和调试记录都会变得难以追踪。

因此，我越来越倾向于把原始文本看成系统中的一种证据源：

模型可以使用这些文本，但不应该随意修改它们。

状态与证据分开保存

在目前的设计中，我尝试让不同类型的信息进入不同的存储层。

SQLite

SQLite 用于保存结构化、需要明确维护的权威状态。

例如一个实体的当前状态、某条关系是否成立、信息的来源和时间等。

这类信息如果散落在自然语言上下文中，很难进行稳定查询和更新，因此更适合结构化保存。

Qdrant

Qdrant 主要用于保存原著证据及其向量表示，支持后续检索。

它解决的是：

当前问题可能和哪些原始文本有关？

而不是：

当前系统的权威状态是什么？

这两个问题看起来接近，但实际职责不同。

一个负责找到可能相关的证据，一个负责保存当前系统认可的状态。

把二者分开以后，系统结构会清楚很多。

当前工作集与长期记忆

在探索过程中，我还尝试区分不同时间尺度的信息。

MVU 用来表示当前工作集，保存交互过程中需要频繁读取和更新的信息。

Memory Books 则用于保存已经完成场景的长期记忆。

这个设计最初是为了减少一个问题：

如果所有历史信息都持续进入当前上下文，系统会越来越臃肿；但如果简单删除旧内容，又可能失去后续真正需要的信息。

因此，我希望不同生命周期的信息能够有不同的去向，而不是全部堆进同一个上下文。

这一部分目前仍然在继续调整。

结构化生成

另一个我重点尝试的问题是：

模型生成以后，结果能不能直接进入系统状态？

我的答案逐渐变成：不能。

自然语言模型的输出本身并不稳定。

即使提示词要求输出固定格式，也可能出现：

  • JSON 格式错误；
  • 字段缺失；
  • 类型错误；
  • 内容虽然格式正确，但语义上和当前状态冲突。

因此，我尝试设计一条更明确的处理链路：

模型输出 → JSON 解析 → Pydantic 结构校验 → 语义检查 → 候选状态

这里有一个很重要的区别：

通过格式校验，并不代表结果就是正确的。

例如：

age: -20

在数据类型上完全可能是合法整数，但语义显然存在问题。

所以结构校验之后，还需要进一步检查：

  • 状态是否与已有信息冲突；
  • 引用的实体是否存在；
  • 时间关系是否合理；
  • 信息来源是否能够追踪。

这也是我第一次比较具体地区分：

“格式正确”与“状态正确”并不是同一件事。

为什么需要候选层

如果模型的生成结果经过一次校验就直接写入权威状态，一旦判断错误，错误就会进入后续所有交互。

而在长时间运行的系统中，这种错误可能不断传播。

因此，我尝试在模型输出和最终状态之间加入一个候选层。

模型生成的新状态先进入候选区域：

生成 → 检查 → 候选 → 确认 → 写入

这样做的意义是把：

模型提出一个状态

和：

系统承认这个状态

区分开。

这也是 NovelST 中我目前比较看重的一点。

失败不是异常情况

在最开始设计系统时，我容易默认：

模型只要按照提示词工作，正常情况下就应该得到可用输出。

后面逐渐发现，更合理的假设其实是：

模型输出失败本身就是系统运行中的正常情况。

因此，目前的设计中考虑了失败重试。

如果输出无法通过解析或者验证，可以重新生成；如果连续失败，则进入隔离状态，而不是继续把有问题的结果传给后续流程。

我把这一过程理解成：

失败 → 重试 → 再验证 → 必要时隔离

这比单纯追求“第一次生成一定正确”更现实。

我开始关心“权威状态”

NovelST 对我影响比较大的一个概念，是“系统里到底什么算数”。

如果：

  • 原著写了一种状态；
  • 历史交互生成了另一种状态；
  • 当前模型又生成第三种状态；

那么最终哪一个才是系统真正认可的状态？

如果没有明确规则，这个系统实际上没有可靠的状态来源。

因此，我开始尝试区分：

  • 原始证据；
  • 当前权威状态；
  • 模型生成候选；
  • 已确认的历史记忆。

这让我逐渐认识到，复杂 AI 应用并不只是：

给模型更多上下文。

它还需要回答很多传统的软件系统问题：

数据存在哪里？ 谁能够修改？ 修改之前怎样验证？ 冲突怎样处理？ 出错以后怎样恢复？

这些问题后来反而成为我在这个项目里最感兴趣的部分。

当前状态

NovelST 目前仍然处于探索和开发阶段，不是已经完成的产品。能够确认的进展是：

  • 完成了 1070 章原始文本的确定性结构解析，形成约 98,630 个稳定段落；
  • 在 20 章语义 / compiler 试点中，17 章生成了成功 artifact；
  • 2 章因语义误标被隔离，另有 1 章尚未运行；
  • SQLite、Qdrant、MVU、Memory Books 与候选状态等内容构成当前设计方向，但完整 Canon / Gate 闭环、全书编译与端到端接入尚未完成。

项目大量借助 AI 编程代理。我主要负责问题定义、架构取舍、约束、Gate 与验收复核；这里不把它描述成独立手写成果。

其中一些模块已有代码或阶段性试验，另一些仍停留在原型或设计阶段。公开页面只记录能够由现有项目记录支持的状态。

这个项目改变了我怎样思考

NovelST 最开始吸引我的是大语言模型。

但随着项目逐渐展开，我花在“模型应该用什么提示词”上的注意力反而开始减少，而越来越多地去思考：

  • 哪些信息应该结构化；
  • 哪些状态必须有唯一权威来源；
  • 检索到的证据怎样和状态对应；
  • 模型生成为什么不能直接修改系统；
  • 怎样验证一次状态变化；
  • 一个失败怎样避免影响后续流程。

这让我开始感觉到，很多 AI 系统真正困难的地方，并不一定是再调用一次更强的模型。

当系统运行时间变长、数据变多、状态开始相互依赖以后，怎样让整个系统保持可理解、可检查和可恢复，本身就变成了问题的一部分。

NovelST 目前没有完成，也还有很多设计需要验证。

但正因为没有完成，我在这个过程中遇到的问题比一个已经整理好的示例项目更真实。

它让我第一次比较持续地思考：

一个依赖大语言模型的系统，怎样才能不仅“能生成”，还能够长期维持自己的状态和边界。
