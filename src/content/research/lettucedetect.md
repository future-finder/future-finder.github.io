## 项目概述

大一下学期开始接触大语言模型幻觉检测后，我逐渐从论文阅读进入实际实验。LettuceDetect 是其中一次比较完整的复现实践。

这次工作的目标很明确：使用 LettuceDetect 的 ModernBERT-base 方案，在 RAGTruth 数据集上完成训练和评测，并检查能否得到与论文报告接近的结果。

整个过程中，我先理解任务和数据，再配置实验环境、训练模型、运行完整测试集，最后整理指标并比较不同任务上的表现。

相比单独理解某个模型结构，这次实践让我第一次真正接触到一条完整的实验链路。
## 任务与数据

实验使用 **RAGTruth** 数据集。

本次完整测试集共有 **2700 条样本**，由三个任务组成：

- 问答：900 条
- 数据到文本生成：900 条
- 摘要：900 条

在整理评测流程时，我首先需要弄清楚两个不同粒度的指标。

**Example-level** 判断一整条回答是否包含幻觉。

**Span-level** 则进一步要求定位具体的幻觉文本片段。

两者看起来都在衡量“幻觉检测”，但实际上对应的任务难度并不一样。前者只需要判断一条回答整体是否有问题，后者还要判断问题具体出现在哪里。

这个区别后来也帮助我理解为什么 Span-level 的指标明显低于 Example-level。
## 实验设置

| 项目       | 设置            |
| ---------- | --------------- |
| 模型       | ModernBERT-base |
| 数据集     | RAGTruth        |
| Python     | 3.11            |
| CUDA       | 13.0            |
| 训练轮数   | 6               |
| 学习率     | 1e-5            |
| batch size | 4               |
| 训练时间   | 1:20:09         |

最初按照 batch size 为 8 运行时出现了显存不足，因此随后调整为 4，训练能够正常完成。

这是一个很普通的问题，但它让我开始意识到，论文中的实验配置并不是脱离实际运行环境存在的。相同的方法最终仍然要落实到具体的显存、依赖、数据和代码环境中。

复现过程中真正需要处理的，也不只是模型本身。
## 复现过程

整个过程大致可以分成几个阶段：

**理解论文和代码 → 配置环境 → 准备数据 → 训练模型 → 完整评测 → 分析结果**

前期主要解决三个问题：

1. LettuceDetect 实际解决的是什么任务；
2. RAGTruth 的数据和标注是怎样组织的；
3. 训练代码与评测代码之间的数据是怎样流动的。

训练完成后，我在 RAGTruth 的 **2700 条完整测试数据**上进行了评测，而不是只运行少量样例。

得到总体结果后，我又分别观察问答、数据到文本生成和摘要三种任务上的表现。

到这个阶段，我关注的问题已经从：

> 模型能不能运行？

逐渐变成：

> 这个结果具体是怎样得到的？它说明了什么？

这也是这次复现过程中比较明显的一次认识变化。
## 实验结果

主要结果如下：

| 指标             | 本次复现 | 论文 Base |
| ---------------- | -------- | --------- |
| Example-level F1 | 76.74    | 76.07     |
| Span-level F1    | 55.59    | 55.44     |

Example-level 的 Precision / Recall / F1 为：

**76.18 / 77.31 / 76.74**

Span-level 的 Precision / Recall / F1 为：

**58.76 / 52.75 / 55.59**

开发集上记录到的最佳 token-level hallucination F1 为：

**0.5990**

从最终结果来看，本次复现与论文中的 base 模型结果非常接近。

Example-level F1 相差约 0.67 个百分点，Span-level F1 相差约 0.15 个百分点。

这个结果基本说明训练和评测的主要链路已经正确复现。如此小的指标差异本身没有必要作进一步解读，因为它不足以说明方法性能发生了有意义的提升。
## 不同任务上的差异

总体 F1 只是实验结果的一部分。

把结果拆分到三个任务以后，可以看到 **Data-to-text 的表现相对较好，而 Summary 更困难**。

| 粒度 | QA F1 | Data-to-text F1 | Summary F1 |
| --- | ---: | ---: | ---: |
| Example-level | 64.77 | 87.59 | 53.76 |
| Span-level | 62.05 | 58.14 | 34.07 |

其中 Summary 任务的幻觉类别 Recall 为：

**0.4902**。在 204 条真实幻觉样本中，模型漏检了 104 条。

也就是说，在摘要任务中，模型仍然漏掉了相当一部分真实幻觉。

这个结果让我开始注意到一个以前很容易忽略的问题：

**一个总体指标正常，并不意味着模型在所有类型的数据上都表现稳定。**

如果只记录最终的 overall F1，就很容易把任务之间的差异压缩成一个数字。

因此，在后面的实验中，我开始更加关注三个问题：

- 指标到底在衡量什么；
- 数据由哪些不同类型的任务组成；
- 错误主要集中在哪些数据和类别上。

这比单独追踪一个最终分数更能帮助我理解模型。
## 实验过程中遇到的问题

这次复现并没有遇到特别复杂的问题，但实际运行过程中存在不少需要逐项处理的细节。

例如：

- Python、CUDA 和 Conda 环境需要正确配置；
- 模型、代码和数据路径需要保持一致；
- batch size 受到实际显存约束；
- 训练完成后还需要确认评测脚本读取的模型和数据是否正确；
- Example-level 与 Span-level 使用不同的评测粒度，不能混为一个指标理解。

这些问题单独来看都不难。

但把它们放在一起以后，我逐渐意识到：

**一次实验是否可信，并不只由模型代码决定。**

环境、数据、资源配置、训练过程和评测口径中的任何一个环节出现偏差，都可能让最终得到的数字失去意义。

这也是我第一次比较具体地认识到“实验可复现性”到底意味着什么。
## 我从这次复现中学到什么

开始这项工作时，我主要关心的是模型方法本身。

做完以后，我对实验的关注范围明显扩大了。

现在再看一个方法，我会先尝试回答下面几个问题：

1. 它到底在解决什么任务？
2. 输入和输出是怎样定义的？
3. 数据是怎样构造和标注的？
4. 训练目标是什么？
5. 最后的指标具体衡量什么？
6. 论文中的方法描述是怎样一步步变成最终实验结果的？

这种变化对我来说比最终得到某个 F1 更重要。

因为只有理解完整的实验链路，我才能判断一个结果为什么成立，也才能继续分析它在哪些情况下会失败。

LettuceDetect 是我第一次比较完整地把论文、代码、环境、训练、评测和结果分析连接起来。它也让我开始把注意力从“模型本身”扩展到支撑模型实验的整个系统。
## 当前进展

目前已经完成的是：

- ModernBERT-base 的训练；
- RAGTruth 2700 条测试数据上的完整评测；
- Example-level 与 Span-level 指标整理；
- 三类任务结果的初步比较。

后续如果继续推进，我更希望进一步分析不同任务之间性能差异产生的原因，并理解模型具体在哪些类型的幻觉上更容易失败。关于数据集任务与评测粒度的整理，见[《理解 RAGTruth》](/research/ragtruth/)。
