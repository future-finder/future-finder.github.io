学习栈的时候，我最开始对它的理解基本停留在“后进先出”。

这个定义当然没有错，但真正开始写表达式相关的题以后，我才逐渐理解为什么栈会反复出现在这一类问题中。

普通数学表达式，例如：

```text
3 + 4 * 2
```

不能简单地从左到右计算，因为不同运算符有不同的优先级。

如果再加入括号：

```text
(3 + 4) * 2
```

计算顺序又会发生变化。

因此，表达式处理真正需要解决的问题不是“如何计算加减乘除”，而是：

> **怎样把运算顺序准确地表示出来。**

栈正好适合保存那些“已经遇到，但暂时还不能处理”的运算符。
## 一、中缀表达式为什么比较麻烦

平时书写的表达式一般都是中缀形式：

```text
a + b * c
```

运算符位于两个操作数之间。

人可以直接根据优先级理解成：

```text
a + (b * c)
```

但程序必须把这个规则明确写出来。

至少需要处理：

- 运算符优先级；
- 左右结合；
- 括号；
- 当前运算符和此前运算符之间的关系。

所以中缀表达式对人比较自然，但并不是最适合程序直接计算的形式。
## 二、后缀表达式

同一个表达式：

```text
a + b * c
```

写成后缀形式是：

```text
a b c * +
```

这里不再需要显式表示优先级。

按照从左到右的顺序计算：

1. 遇到 `a`，保存；
2. 遇到 `b`，保存；
3. 遇到 `c`，保存；
4. 遇到 `*`，取出 `b` 和 `c` 计算；
5. 遇到 `+`，再计算 `a + (b*c)`。

运算顺序已经包含在表达式自身的排列中。

这也是我觉得后缀表达式很有意思的地方：

> **原来需要由优先级规则决定的执行顺序，被转换成了一个可以直接顺序处理的结构。**
## 三、后缀表达式怎样求值

后缀表达式求值比较直接，只需要一个操作数栈。

例如：

```text
3 4 2 * +
```

开始时栈为空。

读到：

```text
3
```

压栈：

```text
3
```

读到：

```text
4
```

得到：

```text
3 4
```

再读到：

```text
2
```

得到：

```text
3 4 2
```

读到 `*` 时，从栈中取出两个操作数：

```text
4 * 2 = 8
```

把 8 压回栈：

```text
3 8
```

最后读到 `+`：

```text
3 + 8 = 11
```

最终栈中只剩：

```text
11
```

因此基本规则可以概括为：

### 遇到操作数

压栈。

### 遇到运算符

连续弹出两个操作数，完成运算，再把结果压回栈。
## 四、一个很容易写错的地方：操作数顺序

如果运算符是：

```text
+
```

或者：

```text
*
```

交换两个操作数通常不会立即暴露问题。

例如：

```text
3 + 5
```

和：

```text
5 + 3
```

结果一样。

但减法和除法不满足交换律。

假设栈顶依次弹出：

```text
a
b
```

那么真正应该计算的是：

```text
b - a
```

而不是：

```text
a - b
```

因此我后来更习惯明确写成：

```c
right = pop();
left = pop();

result = left - right;
```

而不是写两个含义不清楚的临时变量。

变量名本身就可以减少一部分顺序错误。
## 五、中缀转后缀真正难在哪里

相比后缀表达式求值，中缀转后缀要复杂一些。

原因是需要在扫描表达式的过程中决定：

> 当前运算符现在输出，还是暂时留在栈中？

这里需要另一个栈：

**运算符栈。**

如果读到操作数，可以直接加入后缀表达式。

如果读到运算符，则需要和当前栈顶运算符比较优先级。
## 六、基本处理规则

我目前使用的思路可以概括为：

### 操作数

直接输出。

例如读到：

```text
a
```

直接放入后缀表达式。
### 左括号

直接压入运算符栈。

```text
(
```

它相当于建立了一个新的优先级边界。
### 右括号

不断弹出运算符并输出，直到遇到对应的左括号。

最后左右括号本身都不进入后缀表达式。
### 普通运算符

比较它和栈顶运算符的优先级。

如果栈顶运算符应该先执行，就将栈顶弹出并输出。

继续比较，直到当前运算符可以入栈。
### 表达式结束

把运算符栈中剩余的运算符依次弹出。
## 七、用一个例子走完整过程

例如：

```text
a + b * c
```

读取 `a`：

```text
输出：a
运算符栈：空
```

读取 `+`：

```text
输出：a
运算符栈：+
```

读取 `b`：

```text
输出：a b
运算符栈：+
```

读取 `*`。

因为 `*` 的优先级高于 `+`，暂时不能执行 `+`，因此：

```text
输出：a b
运算符栈：+ *
```

读取 `c`：

```text
输出：a b c
运算符栈：+ *
```

表达式结束以后依次弹栈：

```text
a b c * +
```

这就是最终的后缀表达式。
## 八、括号的作用其实是改变“什么时候处理”

例如：

```text
(a + b) * c
```

如果没有括号，`*` 会先于 `+`。

但是读到左括号以后，可以把它理解成：

> 在右括号出现以前，括号内部形成一个暂时独立的处理区域。

因此：

```text
a + b
```

会先转换成：

```text
a b +
```

再和外部的：

```text
* c
```

组合。

最终：

```text
a b + c *
```

从程序实现角度看，括号本身不会进入最终的后缀表达式。

它的作用主要是改变运算符栈的弹出时机。

这个理解对我来说比单纯背：

> 左括号入栈，右括号弹栈

更清楚。
## 九、我写这类程序时会特别检查什么

表达式问题里，我比较容易出错的地方主要有下面几个。

### 1. 数字不一定只有一位

例如：

```text
123 + 45
```

不能把：

```text
1
2
3
```

当成三个操作数。

因此扫描字符串时，需要识别一个完整的数字区间。
### 2. 负数和减号不一定是一回事

例如：

```text
-5
```

中的 `-` 表示负号。

但：

```text
8 - 5
```

中的 `-` 是二元减法运算符。

如果题目允许负数，就需要根据上下文区分二者。
### 3. 括号是否匹配

出现：

```text
(
```

以后是否一定存在对应的：

```text
)
```

如果题目没有保证输入合法，就需要额外处理。
### 4. 栈是否为空

任何 `pop` 操作之前，都应该明确当前栈中是否真的存在足够的元素。

后缀表达式中的一个二元运算符至少需要两个操作数。
### 5. 表达式结束后有没有清空运算符栈

循环读完字符并不代表转换结束。

运算符栈中可能还有尚未输出的运算符。

这是很容易漏掉的一步。
## 十、双栈直接求中缀表达式

除了：

```text
中缀 → 后缀 → 求值
```

还可以直接使用两个栈：

- 操作数栈；
- 运算符栈。

在扫描中缀表达式时，一旦确定某个运算符应该执行，就立即从操作数栈中取出对应数字计算，再把结果压回。

从实现上看，这相当于把：

> 中缀转后缀

和：

> 后缀求值

两个过程合并到了一次扫描中。

我在学习这两种方法以后觉得，它们背后的核心逻辑其实很接近：

> **操作数暂存，尚未到执行时机的运算符也暂存；一旦执行顺序确定，就完成一次归约。**

只是一个先生成显式的后缀表达式，一个直接完成计算。
## 十一、栈在这里真正保存的是什么

学完这些题以后，我对栈的理解不再只是：

> 后进先出的数据结构。

在表达式问题中，它真正保存的是：

> **当前已经出现，但执行时机还没有到的状态。**

例如运算符栈中的：

```text
+
```

不是“不处理”。

而是：

> 我已经知道这个运算存在，只是必须等优先级更高的部分处理结束。

这种“暂存尚未完成的状态”的特点，也解释了为什么栈会出现在：

- 表达式；
- 括号匹配；
- 函数调用；
- DFS；
- 回溯

等很多问题中。

对我来说，这比单独记住某一道表达式题的模板更有价值。
## 当前整理

目前我在表达式相关问题中主要练习过：

- 括号匹配；
- 后缀表达式求值；
- 中缀转后缀；
- 双栈表达式求值；
- 后缀转中缀。

这些问题虽然形式不同，但大部分都围绕同一件事：

> **怎样利用栈保存暂时不能完成的操作，并在合适的时机恢复和处理。**

理解这一点以后，再遇到新的栈题时，我会先尝试判断：

> 当前有哪些信息已经出现，但必须暂时保存，等之后某个条件满足以后再处理？

这个问题往往比“这道题是不是一道栈题”更有帮助。
