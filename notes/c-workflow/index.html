我的 C 语言开发与调试工作流

记录在 Windows、VS Code、GCC 与 GDB 环境中的日常开发和调试流程。

CGCCGDB

刚开始学习 C 语言时，我对“写程序”这件事的理解比较简单：

写代码，点运行，看结果。

后来做的数据结构题越来越长，开始需要处理链表、图、表达式、模拟和各种边界情况以后，我逐渐发现，一个稳定的编程过程不只是把代码写出来，还包括编译、测试、调试和检查。

现在我在 Windows 上写 C 程序时，基本形成了一套比较固定的工作流。

一、我目前使用的环境

我主要使用：

  • Windows
  • VS Code
  • PowerShell
  • GCC
  • GDB

其中 VS Code 主要负责代码编辑和调用各种工具，真正完成 C 程序编译的是 GCC，调试则主要依靠 GDB。

这个区别看起来很基础，但我一开始其实没有完全分清。

以前我容易把 VS Code 理解成一个完整的“编程软件”，后来才逐渐意识到，它更像一个把编辑器、编译器、调试器和终端组织在一起的工作环境。

这个认识也让我更容易理解出现问题时应该去检查哪一层。

例如：

  • 代码错误，检查程序本身；
  • 编译失败，先看 GCC；
  • 调试配置异常，检查 GDB 和相关配置；
  • 输入没有按预期进入程序，再检查终端和输入方式。

把不同工具的职责分开以后，很多问题会清楚一些。

二、从一个干净的代码文件开始

平时刷题或做课程程序时，我更习惯从一个比较干净的文件开始。

基本结构通常只有：

#include <stdio.h>

int main(void)
{
    return 0;
}

然后随着题目需要加入：

  • 结构体；
  • 全局数组；
  • 辅助函数；
  • 其他标准库。

我现在会尽量避免一开始就复制一个很大的模板。

原因是 C 语言程序很多问题来自状态和边界，如果程序里一开始就存在大量与当前题目无关的代码，反而会增加检查成本。

对于大部分题目，我更希望每一部分代码都有明确用途。

三、先让程序稳定编译

写完一个相对完整的部分以后，我通常会先保存并编译，而不是等整道题全部写完再第一次运行。

基本过程可以概括为：

编辑
↓
保存
↓
GCC 编译
↓
处理警告或错误
↓
运行

编译器报错时，我现在会优先处理最前面的错误。

因为很多后续报错只是第一个语法问题造成的连锁反应。

例如少了一个括号以后，编译器可能在后面连续报告很多问题。如果从最后一条开始修改，很容易浪费时间。

所以我的习惯逐渐变成：

先找到第一处编译器真正无法理解的地方。

四、警告也值得看

以前只要程序能够生成可执行文件，我就比较容易忽略 warning。

后来发现，一些看起来不影响编译的警告其实很有价值。

例如：

  • 类型不匹配；
  • 变量可能未初始化；
  • 格式控制符和变量类型不一致；
  • 某些值被隐式转换。

这些问题不一定马上让程序崩溃，但有可能成为后面很难发现的逻辑错误。

所以我现在会尽量把编译警告也当成检查程序的一部分，而不只是处理红色的 error。

五、运行时尽量减少重复操作

需要反复测试程序时，如果每次都手动输入一长串数据，会明显降低效率。

因此我会根据题目情况使用输入重定向。

例如把测试数据放入文件：

input.txt

然后让程序直接从这份输入运行。

这样修改完代码以后，可以快速重复同一组测试，而不用重新输入。

它还有另一个好处：

测试输入本身被保存了下来。

如果某一组数据能够稳定触发错误，就可以反复使用这组数据检查修改是否真正解决了问题。

六、样例通过以后不会立即停止

我现在一般会把测试分成几层。

第一层：题目样例

先确认基本逻辑。

第二层：自己构造的小样例

例如：

  • 一个元素；
  • 两个元素；
  • 空结构；
  • 最小合法输入。

第三层：边界情况

例如：

  • 最大或最小值；
  • 第一个元素；
  • 最后一个元素；
  • 没有满足条件的数据；
  • 所有数据都满足条件。

第四层：更复杂的组合

检查多个操作连续发生以后状态是否还能保持正确。

如果问题适合，还可以进一步做随机测试或差分测试。

这种分层测试比单纯“再随便想几个样例”更稳定。

七、什么时候开始使用调试器

程序出错以后，我不会第一时间打开调试器。

如果问题是：

if (a = b)

这种明显错误，直接检查代码会更快。

我通常在下面几种情况使用 GDB：

  • 某个循环运行若干次后才出错；
  • 链表指针状态不符合预期；
  • 栈顶、队首等状态难以仅靠阅读代码判断；
  • 程序结果错误，但主体逻辑看起来没有明显问题；
  • 需要寻找“第一次出现异常”的位置。

这时候调试器的价值就比较明显。

八、断点应该放在哪里

我以前使用断点时比较随意，哪里觉得“可能有问题”就在哪里停。

后来我逐渐觉得，断点最好围绕一个明确的问题设置。

例如：

我怀疑链表删除以后 curr 指向错误。

那么断点应该放在删除操作前后。

如果怀疑：

表达式处理某个运算符时栈状态异常。

就应该在入栈或出栈的位置停下。

也就是说：

先提出一个关于程序状态的猜测，再用断点验证。

而不是打开调试器以后漫无目的地逐行执行。

九、我最常看的变量

进入调试状态后，我一般不会同时盯着所有变量。

会优先观察真正决定当前状态的几个量。

例如链表：

prev
curr
next

栈：

top
stack[top]

图遍历：

current node
visited[]
queue / stack

模拟题：

当前位置
当前状态
循环计数

如果有几个变量需要长期观察，我会加入 Watch。

这样程序每执行一步以后，可以直接看到这些状态怎样变化，而不需要反复寻找变量。

十、寻找第一次偏离，而不是最终错误

这是我现在调试时最重要的习惯之一。

假设程序最终输出：

37

但正确答案应该是：

42

只盯着最终的 37 很难得到信息。

我会尝试寻找：

从哪一步开始，程序里的状态第一次和我手算的结果不一样？

例如：

前 8 次循环都正确，第 9 次开始错误。

那么真正的问题大概率就在第 9 次附近，而不是最终输出的位置。

所以调试时我更关注：

first wrong state

而不是：

final wrong answer

这种方法尤其适合状态较多的程序。

十一、修改一次，只重新验证一个假设

以前调试程序时，我有时会一次改几个地方：

  • 调整循环条件；
  • 修改初始化；
  • 改一个判断；
  • 顺手重写一段代码。

如果结果突然正确，我反而不知道真正的问题是什么。

现在我更希望每一次修改都有明确理由：

我认为这里的循环少处理了最后一个元素，所以只修改循环边界。

然后重新运行。

如果问题解决，就能确认自己的判断。

如果没有解决，再继续寻找其他原因。

这样虽然单次修改看起来慢一点，但整个调试过程更容易保持清楚。

十二、我的日常流程

如果把目前的习惯压缩成一条完整流程，大致是：

理解题目
↓
设计数据结构和主要状态
↓
编写代码
↓
保存
↓
GCC 编译
↓
处理 error / warning
↓
运行样例
↓
测试最小和边界数据
↓
定位异常
↓
必要时使用 GDB
↓
观察关键状态
↓
修改一个明确问题
↓
重新测试

如果程序比较复杂，我还会再增加：

随机测试 / 差分测试

十三、一些提高效率的小习惯

在 VS Code 中，我现在也会使用一些比较简单但高频的操作：

  • 快速保存；
  • 快速注释；
  • 移动代码行；
  • 复制当前行；
  • 重命名变量；
  • 快速打开文件；
  • 打开终端；
  • 单步调试。

这些操作本身没有什么技术含量，但当每天需要反复编辑、编译和调试程序时，减少重复操作还是能节省不少注意力。

我更愿意把它们看成一种基本的工具熟悉度，而不是单独需要学习的“技能”。

我目前对这套工作流的理解

以前我容易把“编程能力”主要理解成：

能不能想到算法，以及能不能把代码写出来。

现在我觉得还缺少后半部分：

写出来以后，怎样确认它真的正确？

这也是为什么我的工作流逐渐从：

写代码 → 运行

变成了：

写代码 → 编译 → 测试 → 观察 → 定位 → 验证

工具本身并不是重点。

GCC、GDB、VS Code 都只是在帮助我更快地回答一个问题：

程序现在究竟处于什么状态，它为什么会得到这个结果？

我现在仍然会写出边界错误、初始化错误或者逻辑遗漏。

但相比单纯依赖反复重读代码，我已经越来越习惯把问题拆开，用测试和程序状态逐步定位。

这套工作流也还在继续调整。

程序已经出现错误时，我会配合使用《我的 C 语言程序检查与调试清单》，按固定顺序缩小范围。
